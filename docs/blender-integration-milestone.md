# AGS3D Blender Integration Milestone — Design Document

## Goal

Let artists author a room's full visual layer — geometry, materials, lighting,
and animation — inside Blender, while tagging gameplay objects (navmesh,
blockers, points, cameras, hotspots, trigger regions, spawn points) using a
dedicated Blender add-on. A single export step produces a `.glb` visual asset
and an updated `.agroom` file that AG Studio and `ag build` can immediately use.

At milestone end an artist can:

1. Model a room in Blender, tag all gameplay elements using the AGS3D panel.
2. Run **Export AGS3D Room** — Blender writes `rooms/<name>/<name>.glb` and
   updates `rooms/<name>/<name>.agroom`.
3. Open AG Studio — the room editor shows the visual mesh from the `.glb` and
   all gameplay gizmos from the `.agroom`.
4. Round-trip: gameplay edits made in AG Studio can be re-imported back into
   Blender to sync object positions.

---

## Architecture

```
Blender (artist's tool)
├── AGS3D add-on (Python)
│   ├── Object type panel    tag any Blender object as AGS gameplay element
│   ├── Viewport overlay     colored wireframe per type in Blender viewport
│   ├── Export operator      → rooms/<name>/<name>.glb  (visual)
│   │                        → rooms/<name>/<name>.agroom  (gameplay)
│   └── Import operator      ← rooms/<name>/<name>.agroom  (sync back)
│
└── Blender GLTF exporter    standard Blender .glb export (meshes, mats, lights)

rooms/<name>/
├── <name>.blend             Blender source file (optional, not required by AGS)
├── <name>.glb               exported visual + lights
├── <name>.agroom            gameplay data — single source of truth
├── <name>.agscript          room logic
└── <name>.tscn              generated by ag build (references .glb)

AG Studio (Godot editor)
└── Room editor
    ├── Loads .tscn which embeds .glb visual mesh as a sub-scene
    ├── Shows AGS gameplay gizmos from .agroom on top
    └── "Re-import from Blender" button — re-runs ag build on the room
```

**Source of truth rules:**

- **`.agroom`** is the single source of truth for gameplay data. Both Blender
  and AG Studio write to it; neither silently clobbers the other.
- **`.glb`** is the visual asset — only Blender writes it.
- **`.blend`** is optional and never read by the AGS3D toolchain; it is the
  artist's working file.

## Blender Add-on

### Installation

Targets **Blender 4.x** using the Extension system (`blender_manifest.toml`).
Installable via Blender Preferences → Extensions → Install from Disk, or from
the AGS3D extension repository when published.

Add-on source lives at `tools/blender_addon/` in the monorepo.

---

### F1 — Object Type Panel

A dedicated panel in the **Object Properties** sidebar (Properties → Object →
AGS3D) and mirrored in the **N-panel** sidebar (View3D → N → AGS3D tab) for
quick access while modeling.

**Panel layout (per selected object):**

```
AGS3D Object
  Type: [ None ▾ ]
  ─────────────────
  (type-specific fields appear here)
```

**Type options and their fields:**

| Type | Fields |
|---|---|
| `None` | — (default; object exported as visual geometry) |
| `WalkableSurface` | Name |
| `BlockerVolume` | Name |
| `Point` | Name |
| `Camera` | Name; look_at target (eyedropper — pick an Empty in scene) |
| `Hotspot` | Name |
| `TriggerRegion` | Name |
| `SpawnPoint` | Name; Character (text field — maps to .agchar name) |
| `NavMesh` | — (marks object as the baked navigation mesh; one per room) |
| `VisualMesh` | — (explicitly mark as visual-only; excluded from gameplay export) |
| `Light` | — (marks a Blender light for export; exported via GLTF) |

Custom properties (`AGS_type`, `AGS_name`, etc.) are stored on the Blender
object so they persist in `.blend` files and survive Blender restarts.

**Camera look_at:** Blender cameras look down their local −Z axis. The exporter
can compute the look_at point automatically as
`look_at = camera_world_position + camera_forward * 5.0`. Alternatively, the
author can pick an Empty as an explicit look_at target using the eyedropper —
this is preferred when precision matters.

### F2 — Viewport Overlay

A custom overlay drawn in the Blender 3D viewport (registered via
`bpy.types.SpaceView3D.draw_handler_add`) that shows AGS gameplay objects as
solid wireframes in type-specific colours, matching the AG Studio gizmo colours.

| Type | Colour |
|---|---|
| WalkableSurface | Green |
| BlockerVolume | Red |
| Point | White diamond + name label |
| Camera | Yellow frustum + look_at line |
| SpawnPoint | Cyan figure icon |
| Hotspot | Blue outline |
| TriggerRegion | Purple outline |
| NavMesh | Teal transparent overlay |

The overlay is toggled via **View → Overlays → AGS3D** (a toggle added to
Blender's overlay dropdown).

---

### F3 — Navigation Mesh Baking

The navmesh defines where characters can walk. Authors mark one mesh as
`NavMesh` type. If no `NavMesh` object exists, the exporter automatically
projects a walkable area from the floor `WalkableSurface` objects.

**Manual workflow:** Model the exact walkable floor (may include stairs,
slopes, raised platforms). Tag it as `NavMesh` in the AGS3D panel. The
exporter includes it in the `.glb` with the reserved name
`AGS_NavMesh` — Godot's `AGSWalkableSurface` recognises this name and uses
the mesh as its navmesh source instead of generating a flat box.

**Auto-bake button (in panel):** Uses Blender's built-in navmesh baking
(`bpy.ops.mesh.navmesh_make`) on the floor geometry, creates a new mesh tagged
as `NavMesh`.

### F4 — Export Operator

**Menu:** `File → Export → AGS3D Room (.agroom + .glb)`

**What it does:**

1. **Validate** — check that all AGS-tagged objects have names; warn if
   `initial_camera` is unset; warn on duplicate names within a type.

2. **Export `.glb`** — call the standard Blender GLTF exporter with settings:
   - Include: meshes, materials, lights, empties tagged as look_at targets.
   - Exclude: objects with `AGS_type` set to a gameplay-only type
     (BlockerVolume, Hotspot, TriggerRegion, etc.) — these are invisible in
     gameplay and do not need visual geometry exported.
   - Apply modifiers, triangulate, export Y-up → Z-up transform (Godot uses
     Z-up; the Godot GLTF importer handles this, so the exporter uses standard
     Blender GLTF settings).
   - Output: `rooms/<name>/<name>.glb`.

3. **Write / merge `.agroom`** — extract gameplay object data from Blender:
   - Read any existing `.agroom` (to preserve fields that Blender doesn't own,
     e.g. `script` entries, comments).
   - Overwrite geometry-derived fields: positions, sizes, camera look_at.
   - Write the merged result to `rooms/<name>/<name>.agroom`.

4. **Coordinate system** — Blender is Y-up, right-handed. Godot is Y-up,
   left-handed. The exporter applies the same axis flip as the standard GLTF
   exporter (`X → X`, `Y → Z`, `Z → −Y` in game space). All positions written
   to `.agroom` use Godot coordinates.

5. **Size extraction** — for volume types (BlockerVolume, Hotspot,
   TriggerRegion, WalkableSurface), the exporter reads the object's bounding
   box in local space (after applying scale) to derive the `size` field.

**Export dialog options:**

| Option | Default | Description |
|---|---|---|
| Project root | auto-detect from .blend path | Root directory containing game.agp |
| Room name | inferred from collection or .blend filename | Written to .agroom |
| Export visual mesh | on | Write .glb |
| Export gameplay data | on | Write .agroom |
| Overwrite existing .agroom | merge | `merge` keeps non-geometry fields; `overwrite` replaces entirely |

### F5 — Import Operator

**Menu:** `File → Import → AGS3D Room (.agroom)`

**What it does:** Reads an `.agroom` file and creates Blender objects for each
gameplay element, tagged with appropriate `AGS_type` custom properties.

- Each gameplay element becomes a Blender **Empty** (arrows display type)
  or a **Mesh** (for volume types — a simple box matching `size`).
- Objects are placed in a Blender collection named `AGS_Gameplay`.
- Existing objects in `AGS_Gameplay` are removed and replaced (full re-sync).
- Visual geometry in other collections is untouched.

**Use case:** An artist receives a `.agroom` file that was edited in AG Studio
(gameplay positions tweaked) and wants to sync those positions back into their
`.blend` file before making new visual changes.

---

### F6 — Character Animations

**What it does:** Lets an artist rig a character in Blender and export
walk/idle/talk animation clips as part of the character's `.glb`. The
`.agchar` file references these clips by name.

#### `.agchar` additions

```
Character "player" {
    display_name   = "Player"
    mesh           = "characters/player/player.glb"
    animations = {
        idle  = "Idle"
        walk  = "Walk"
        talk  = "Talk"
    }
}
```

#### Blender workflow

1. Rig character, create NLA tracks named `Idle`, `Walk`, `Talk`.
2. **Export AGS3D Character** (`File → Export → AGS3D Character (.glb)`):
   - Exports armature + mesh + all NLA actions as GLTF animation clips.
   - Output: `characters/<name>/<name>.glb`.
3. AG Studio character editor gains an **Animations** section listing the
   clip names and a preview button.

#### Runtime

- `ags_character.gd` uses `AnimationPlayer` to drive the clips:
  - `idle` plays when velocity is zero.
  - `walk` plays when navigating; playback speed scales with move_speed.
  - `talk` plays during `say()` / `think()`.

### F7 — AG Studio Integration

AG Studio's Room editor gains Blender-aware features:

#### .glb visual mesh display

When `rooms/<name>/<name>.glb` exists, `ag build` embeds it into the
generated `.tscn` as a `PackedScene` (sub-scene node) at the room root.
The Room editor 3D viewport then shows the full visual mesh alongside the
AGS gameplay gizmos.

**`.tscn` addition generated by `ag build`:**

```
[ext_resource type="PackedScene" path="res://rooms/start/start.glb" id="Visual_1"]
...
[node name="Visual" parent="." instance=ExtResource("Visual_1")]
```

#### "Re-import from Blender" button

A button in the Room editor toolbar. Clicking it:

1. Checks if `rooms/<name>/<name>.glb` is newer than `rooms/<name>/<name>.tscn`.
2. If so: re-runs `ag build <agroom_path>` and reloads the scene.
3. Displays a timestamp of the last import in the toolbar tooltip.

#### Conflict indicator

If `.agroom` was modified in AG Studio after the last Blender export (detected
by comparing file modification times), the Room editor shows a yellow banner:

> "Gameplay data has been edited in AG Studio since last Blender export.
>  Re-exporting from Blender will overwrite these changes unless you use
>  merge mode."

## Workflow Examples

### New room, visual-first

1. Model room in Blender.
2. Tag floor as `WalkableSurface "floor"`, wall boxes as `BlockerVolume`, add
   a Camera empty, Point empties for door/window, SpawnPoint for player.
3. **Export AGS3D Room** — writes `start.glb` + `start.agroom`.
4. Open AG Studio — room editor shows visual mesh + gizmos. Write script. Press Play.

### Existing room, adding visuals

1. Author has `start.agroom` authored in AG Studio.
2. Artist runs **Import AGS3D Room** in Blender — gameplay objects appear as
   empties/boxes in `AGS_Gameplay` collection.
3. Artist models visual geometry around them, bakes navmesh.
4. **Export AGS3D Room** (merge mode) — positions updated from Blender, visual
   mesh written; AG Studio edits (script references, etc.) preserved.

### Character with animations

1. Rig character, create NLA actions `Idle`, `Walk`, `Talk`.
2. **Export AGS3D Character** → `player.glb`.
3. Update `player.agchar` with `mesh` path and `animations` mapping.
4. `ag build` embeds the mesh in the character `.tscn`.

## Stub: Animation Frame Tags

> **Status: feasibility not yet assessed.** Do not implement until the stub is
> promoted to a full spec.

### What it would do

Let an artist tag specific keyframes in a Blender animation clip with named
events. The runtime fires those events as the animation plays — useful for:

- **Footstep sounds** — trigger `PlaySound("step_left")` on the exact frame
  the foot contacts the floor in the walk cycle.
- **Action sounds** — sword swing, door knock, item pickup sounds synced to
  their visual moment.
- **Script callbacks** — emit a named signal at a specific frame so an
  `.agscript` function can react (e.g. start a dialogue exactly when a
  character reaches a table).
- **UI / button events** — trigger a button press response on the frame an
  interaction animation reaches its apex (feasibility uncertain — see risks).

### Proposed approach

**In Blender:** use Blender's per-action **pose markers**
(`action.pose_markers`) to tag frames with a string label.
Example: frame 12 → `"sound:step_left"`, frame 24 → `"signal:picked_up"`.

**Export problem:** glTF 2.0 has no native animation event/marker track.
Two options:

1. **GLTF custom extension** (`AGS_animation_events`) — embed the marker list
   in the GLTF extras JSON. Godot's GLTF importer would need to read and
   preserve this data (requires a Godot `GLTFDocumentExtension` plugin).

2. **Sidecar file** — export a `characters/<name>/<name>.aganim` JSON file
   alongside the `.glb` listing clip names → frame → event label. `ag build`
   reads it and injects Godot `AnimationPlayer` **method call tracks** into
   the character `.tscn` at the correct frames.

Option 2 (sidecar) is simpler and avoids modifying the GLTF importer, but
adds another file to the pipeline. Option 1 is cleaner but requires more
engine work.

**In Godot:** `AnimationPlayer` natively supports **method call tracks** —
they call a named method on a target node at a specific frame. The runtime
script (`ags_character.gd`) would expose an `_on_anim_event(label: String)`
method that parses the label prefix and dispatches:

| Label prefix | Action |
|---|---|
| `sound:<name>` | `AGSRuntime.play_sound(name)` |
| `signal:<name>` | emit `animation_event(name)` signal on AGSCharacter |
| `script:<fn>` | call `fn()` on the room script (feasibility uncertain) |

### Risks and open questions

- **GLTF round-trip**: pose markers are Blender-internal and not part of the
  glTF spec. Either approach (extension or sidecar) adds pipeline complexity.
- **UI/button events**: calling into room scripts from inside an animation
  track requires the character to hold a reference to its parent room script,
  which may create coupling issues. Needs design review before implementing.
- **Billboard sprites**: frame tags on sprite animations would need a different
  mechanism (no `AnimationPlayer` for billboards — frame selection is driven
  by code). The dispatch approach may need to be generalised.
- **Timing precision**: Godot's method call tracks fire on the nearest
  physics frame, not at sub-frame precision. For audio sync this is acceptable
  (~16 ms at 60 Hz); for visual-critical events it may not be.

### Promotion criteria

Promote to a full implementation task when:

1. A concrete use case in the game requires frame-tagged sounds or signals
   (not just "nice to have").
2. The sidecar vs GLTF-extension question is decided.
3. The billboard sprite case is addressed or explicitly deferred.

## Out of Scope

- Real-time Blender–Godot live-link (viewport sync without export step).
- Blender material system → Godot shader translation (materials export as
  standard PBR via GLTF; complex shader graphs are not translated).
- Blender physics simulation baking (cloth, fluid, particles).
- LOD (level of detail) generation.
- Blender geometry nodes procedural rooms (geometry is baked on export).
- Facial rigging / morph targets (deferred to a later animation milestone).
- Multiplayer / networked room sync.
